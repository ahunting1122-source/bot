## 3. 解决方案与优先级

### P0 · 可信地基（先做，其余都建在这上面）

**A1 站点样本 ×10 + 重复跑方差** — 做法：选 5 类站点（文档站 / 电商 / 论坛 / 需登录后台 / 反爬严），每类跑同一个「搜索 → 翻页 → 进详情 → 抽字段」；同一用例连跑 5 次出成功率与方差。**验证**：每个站点有稳定性数字，而非单次通过。**成本**：主要是时间与站点选择，无代码改动。**风险**：反爬站点可能直接失败，需接受"记录了失败也是结论"。

**A2 预取召回** — 做法：先加埋点统计"预取注入了但模型没用"vs"预取没命中"的比例，再决定是调 `PREFETCH_MIN_SCORE` / `PREFETCH_TOP_K`，还是承认预取对"追问型任务"本来就该让位给工具检索。**注意**：这条**必须排在 D2 修复之后重新测量**（见 §4）。

**A3 EXTRACT_JS 提炼质量** — 做法：把 `readable_text` 的兜底从"只用 `structured`"改成"`structured` 与 `text` 取更可信的一个"（加长度比例门槛），并在 `chunks` 上记一条 `extract_path` 便于回查。**风险**：纯 `text` 噪声更多，可能拉低精确率 → 需用 A1 的语料回归。

**B1 产物入口** — 做法：不复活 TaskPanel，改在对应 assistant 消息下渲染本次任务的 artifacts（名称 + `/api/artifacts/{id}` 下载）。后端加一个按 `task_id` 取 artifacts 的只读接口即可。**成本低、用户可感收益高**，我建议提到 P1 首项。

**B4 审计时间线** — 做法：后端按任务聚合对外动作（站点 / 动作 / 时间 / 结果 / 前后截图），前端一个只读页。数据都在，只缺视角。

### P1 · 功能闭环

**B2 历史检索补全** — 给 `history_search_tasks` 加 `since`/`until`/`conversation_id`/`status` 参数，并把检索面从 `goal` 扩到"报告文件名 + 报告正文"（正文已在 `chunks` 里，可直接复用 FTS5 双路）。**验证**：新增 2 个用例（按时间找、按文件名找）。

**B3 记忆 scope** — 加 `scope`（global / project）+ `source_message_id` + `status`；`build_context` 按 scope 过滤。**注意**：要写迁移（`0005` 已被向量表占用 → 顺延 `0006` 或与向量表合并编号，需先冻结）。

**C1 单 worker 抢占** — 关键认知：浏览器是**全局单例**，两个任务物理上不能同时用一个浏览器，所以"抢占"本质是**串行调度**而非并行。方案：给队列加优先级 + 允许"用户新消息让当前任务挂起（`interrupt` 已有）→ 跑完新的再恢复"。**风险**：挂起点的幂等与浏览器状态必须一致，别把 B1/D1 那类竞态引入新位置。

### P2 · 能力扩展

**Skill 层（#1）** — 建议**只做"读"这一半**先：加载器 + `skill_load` + prepare 注入简述（上限 5）+ 手工写 3 个技能。理由：① 它是 MCP prompts 的前置；② 它能拿 A1 的站点样本做"第二遍步数更少"的量化验证；③ `skill_save` 的四道闸（查重、矛盾转备选、注入择优、降级淘汰）复杂度高，留到第二步。**验证**：同站第二遍步数 < 第一遍（`ARCHITECTURE.md` 16.7 有基线）。**风险**：技能简述会重新撑上下文 → 必须卡上限 5 且只注入相关。

**向量路（#2）** — 建议**先不上，只埋点**。理由是新的：**D2 修好后，"FTS5 召回不行"这个既有结论全部作废了**——之前测到的 0 召回是**索引 bug**，不是检索能力上限。所以"FTS5 够不够"必须在修复后的真实语料上**重新测一遍**，有 ≥5 个真实 badcase 再上向量。**成本**：sqlite-vec 依赖 + 本地模型下载几百 MB + CPU 推理延迟。

### P3 · 探索（暂不动）

子 Agent、多模态、定时任务/无人值守、接管日常浏览器——都写在 `ROADMAP.md` 里，且前三项各依赖 P0/P2 的产出。**多模态**与**视觉兜底**共享一个决策（坐标点击需要模型能"看"），建议一起拍板。

## 4. 依赖关系（关键前置链）

```
D2 修复（已完成）──→ 重新测量 FTS5 真实召回 ──→ 才谈要不要上向量
站点样本 ×10 ──────→ Skill 层「第二遍更快」的量化验证
Skill 层 ─────────→ MCP prompts 作技能来源
多模态决策 ────────→ 视觉兜底（截屏 + 坐标点击）
Skill 层 + 单 worker 抢占 ──→ 子 Agent
```

**一句话**：能力扩展不该抢在可信地基前面——`ROADMAP.md` 自己的结论也是这个。

## 5. 需要拍板

1. **读还是写？** 只做"收集整理"风险低；一旦涉及站内提交/下单，审计与撤销必须先行（B4 就是为它铺路）。
2. **深还是广？** 一个站点做到极致，还是十个站点都凑合用？（决定 A1 怎么选样本）
3. **要不要无人值守？** 定时任务意味着你不在场时它也在动你的账号——安全与暂停机制得先设计。
4. **要不要碰你日常浏览器的登录态？** 省掉重复登录，但拆掉专用 Profile 的隔离墙。
5. **多模态与视觉兜底一起上还是都不上？**（两者耦合，分开决策会互相拖后腿）

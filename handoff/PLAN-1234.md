## 1.1 每个问题的后果与解法（详细）

### 问题 1 · 权限仍是事前确认流

**现象**：`agent.py:288` gate 里 `if not question and tool.confirmation and not self.registry.granted(call["name"])` 会 `interrupt()` 等批准；`ui_smoke.py:339 chat_approval` 用例专门验证审批；`eval_run.py` 把 `approval` 计入 `confirmations` 指标。

**后果**：
1. 与 00-CONTEXT 硬约束①（事前零确认）直接矛盾，v1 的定位没落地。
2. 无人值守跑批不稳——每个 `browser_click` / `browser_fill` 都可能挂起，`eval_run` 与 `agent_probe` 靠自动批准绕过去，掩盖了真实的人工介入频率。
3. 长任务被切碎：`interrupt` 会结束当前图调用并回 `WAITING_USER`，恢复要重进 gate，每一步多一次进程往返。
4. **预算成为唯一刹车**这件事没有被真实检验过；不切权限，P1-6 的预算就是纸面功能。
5. 越晚切，耦合越深：UI 文案、SSE 事件、测试断言、评估指标四处都要跟着改。

**解法**：P1-8，一步到位但单独提交。
- gate 只留两条人工路径：模型主动 `ask_user`、工具返回 `needs_user`。
- `Tool.confirmation` 字段、`GRANTABLE_TOOLS`、`load_grants` **代码保留**，但策略改为全放 → 它们退化为「审计分组标签」（对外动作清单里按站点分组用）。
- MCP 的 `confirmation=not auto_approve` 保留字段，v1 全视为开启。
- 同步改三处：`tests/test_grants.py`（断言从"要求确认"改为"不再要求确认，且仍写入审计"）、`ui_smoke.py` 的 chat_approval 用例（改为验证零确认完成 + 审计清单可见）、`eval_run.py` 的 `confirmations` 改名 `audit_actions`（`drain()` 里 `waiting_user` 分支保留，只处理 `needs_user`）。
- 验收：两个真实多步任务全程零人工确认完成；UI 检查仍 13 组。

### 问题 2 · `observe()` 只给纯文本

**现象**：`browser.py:327` `text = (await page.locator("body").inner_text())[:14000]`，返回体只有 `url/title/text/version/elements/screenshot_id`。

**后果**：
1. 03 的三层切块里的第①层（结构切）没有输入源，只剩「空行/定长」，等于规则退化成第②层。
2. 表格被拦腰切断——inner_text 里表格变成一串没有分隔的行，`|` 结构丢失，「整表一块 / 大表重复表头」两条规则完全失效。
3. `title_path`（`H1 > H2`）拼不出来，检索命中后无法告诉模型"这段来自哪个小节"。
4. 方向 6 明确写过：中文向量召回的效果依赖切块质量，切块不成立，向量那一层就是白加。

**解法**：P3-1。
- 扩展 `OBSERVE_JS`（或新增 `EXTRACT_JS`）产出 markdown 化正文：`h1-h3 → #`、`li → -`、`tr → |`、`p → 段落`。
- 守卫一：放进 result 的**独立键** `structured`，由 `ToolResultPolicy.project()` 在构建模型上下文前剥离 → 模型看到的仍是 `text`（14000 上限不变），上下文成本不涨。
- 守卫二：`structured` 截 24000 字符（够索引够切块，不无限膨胀）。
- 守卫三：提取失败只记日志，沿用现有 `suppress(Exception)` 的容错风格，绝不让它影响 observe 主结果。
- 验收：fixture 页面单测结构化输出；断言模型上下文里不含 `structured`；browser 生命周期测试不回归。

### 问题 3 · trigram 对中文短查询空召回

**现象**：实测 `MATCH '机械键盘'` 命中；`MATCH '键盘'`、`'键'`、`'B站'` 全部 0 条。

**后果**：
1. 中文最常见的查询形态就是 2 字词（键盘、显卡、机票、B站）→ FTS 路大范围漏召回。
2. recall@5 天生偏低，而且**会误导技术判断**：看起来"检索不行，必须上向量"，真实原因一半在索引层，上了向量也救不回 FTS 该出而没出的候选。
3. 检索被模型判定为"没用"，04 的引用回填硬约束就会大面积触发"未引用来源"提示，反而伤体验。

**解法**：P3-2 / P3-4 / P4-1。
- `chunks` 加 `char_text` 列：CJK 逐字插空格、拉丁数字保持整词（`机械键盘推荐 B站 评测` → `机 械 键 盘 推 荐 B 站 评 测`）。
- 建**两张** FTS 表：`chunks_fts_trigram` 索引 `text`、`chunks_fts_chars` 索引 `char_text`（FTS5 的 tokenizer 是表级选项，不能靠单表加列）。
- 查询侧用**同一个切分函数**处理后按 phrase 查询（`键盘` → `"键 盘"`）。实测：`键盘` 命中 3 块、`键` 命中、`B站`/`b站` 命中且大小写不敏感。
- 两路各自出候选，交给 04 的 RRF 融合排名。

### 问题 4 · `chunks` 缺 `conversation_id` / `task_id`

**现象**：03 定的字段是 `(id, source_type, source_id, host, ordinal, text, tokens, hash, origin, title_path, created_at)`。

**后果**：
1. 04 要求「默认按当前会话/站点收窄，全局检索需显式」——没有 `conversation_id` 就只能全库检索，历史任务的所有网页正文都会灌进上下文，噪声撑爆预算（这正是 04 要防的事）。
2. 表建好再补列要写迁移**并回填历史数据**（`source_id` 是 tool_results/artifact 的 id，反查会话要 join 两跳）。

**解法**：P3-2。表还没建，直接把 `conversation_id`、`task_id` 建进去，digest 写索引时从 task 上下文带下去；`local_file` / `skill` 两类允许为空。检索侧 scope 的三档（会话 / 站点 / 全局）由此都有落点。

### 问题 5 · 评估指标缺事件承载

**现象**：`eval_run.py:71 drain()` 唯一的输入是 `/api/tasks/{id}/events` 的 SSE 事件流。

**后果**：
1. 04 要的 recall@5 与引用覆盖率没有数据来源，只能人工看日志 → 无法作为回归门槛。
2. 而这两个指标是判断"检索有没有真被用起来"的唯一客观依据：只看 10 用例通过，无法区分"模型没检索也答对了"和"检索真起了作用"。

**解法**：P4-5 / P4-6。
- 服务端新增两个事件：`retrieval_injected`（本条注入了哪些 origins + 分数）、`citation_checked`（matched / missing）。
- `drain()` 增加两个分支收集这两个事件；`report()` 加两列；`eval_cases.json` 的检索类用例加 `expect_origins`。
- 新增一个检索用例（"上次 B 站搜到的键盘信息再整理一遍"），让指标有真实流量。

### 问题 6 · `nodes.py` 是三方共享热点文件

**现象**：01 新建 `app/graph/nodes.py`；03 要在 digest 后挂索引写入；04 要在 prepare 挂预取。

**后果**：三个对话并行改同一文件 → 合并冲突、互相覆盖。最典型的失败形态：后合入者的 prepare 版本把先合入者的 digest 改动冲掉，而且**测不出来**（测试各自跑自己分支时都是绿的）。

**解法**：约定写死在 §7。
- P1-1/P1-2 把扩展点固化为 policy 调用：`AgentRunner.__init__` 注入 `ToolResultPolicy` / `Retriever` / `Indexer`，节点里只写 `await self.policies.xxx(...)`。
- 03/04 各自只加**一处**调用行，不重构该文件；`nodes.py` 的结构性改动只允许方向 1+2 做。

### 问题 7 · `Operation` 与 `tool_results` 语义重叠

**现象**：`tool_calls`(Operation) 表已经存了 `operation_id` / `name` / `status` / `args` / `result`(JSON)。

**后果**：
1. 两处真值会漂移：幂等该信谁、审计该信谁，说不清。
2. `02` 文档写的"digest 挂在 `ToolRegistry.execute()` 末尾"与 `01` 的"digest 是图节点"会同时存在 → 同一份结果被写两次，或者一处悄悄不生效。

**解法**：
- 分工写死：`Operation` = 控制流与幂等（**现状不动**）；`tool_results` = 原文 / bytes / tokens / hash / 引用登记，**digest 是唯一写入口**，checksum 判重。
- 不采用"挂在 registry.execute 末尾"（那是 01 未完成时的兜底路径，本计划不采纳），保证编排层与工具层的边界不糊。

### 问题 8 · 两个方向认领同一个 revision + 迁移写法有硬约束

**现象**：01 与 02 的文档都写 `0003`；FTS5 虚拟表无法用 SQLAlchemy 建模；`migrations/env.py` 走 `create_engine` + `database_url`，没有 autogenerate。

**后果**：
1. 两个编号相同的 revision 文件合入时，alembic 报 `Multiple revisions with the same id` → 而 `main.py:61 migrate()` 是在 lifespan 里跑的，**服务直接起不来**（不是隐式降级，是硬失败）。
2. FTS 表若用 SQLAlchemy 建 → 根本建不出来（虚拟表必须 `CREATE VIRTUAL TABLE`）。
3. external content 表缺同步触发器 → FTS 与主表静默失同步：查询结果慢慢变错，但**不报任何错**，最难查。

**解法**：§2 冻结编号 + 写法定死。
- `0002 → 0003`(tool_results，方向1+2) `→ 0004`(chunks，方向3) `→ 0005`(占位给方向6 向量)。
- FTS5 一律 `op.execute()` 手写 SQL；必须同时建 `AI`/`AD`/`AU` 三个触发器；`downgrade` 要 drop 虚拟表 + drop 主表（测试库反复重建）。
- 表用 `row_id INTEGER PRIMARY KEY AUTOINCREMENT` + `id TEXT UNIQUE`：TEXT 主键在 REPLACE 语义下 `rowid` 会变，会让 FTS 行变孤儿。

## 2. 表与迁移编号（先冻结，防撞车）

| revision | 内容 | 归属 |
|---|---|---|
| `0001` `0002` | 已存在 | — |
| `0003_tool_results` | `tool_results` 表 | 方向 1+2 |
| `0004_chunks` | `chunks` + `chunks_fts_trigram` + `chunks_fts_chars` + 三个同步触发器 | 方向 3 |

规则：

- 一个对话只写自己的 revision，`down_revision` 严格指向上一个。
- **FTS5 虚拟表必须用 `op.execute()` 手写 SQL**（SQLAlchemy 不建模虚拟表）；`env.py` 走的是 `create_engine` + `database_url`，无 autogenerate。
- external content 表必须同时建 `AI`（insert）/`AD`（delete）/`AU`（update）三个触发器，否则 FTS 与主表静默失同步。
- 每个迁移都要能 `downgrade`（drop 虚拟表 + drop 表），因为测试库反复重建。

### 切块规则（P3-3 细则）

- ① 结构切：markdown 标题、段落、列表项、表格行、空行；**`structured` 缺失时退回纯文本的空行/行结构切**（兼容 D3 落地前的旧数据与 local_file）。
- ② 合并到 300–500 中文字；超 512 token 在句子边界再切（口径：中文字数 ≈ token，方向 6 对齐 bge 512 时再校准）。
- ③ overlap 50–100 字。
- 特例：整表 ≤500 字一块；大表按行组切且**每块重复表头**；块首拼标题路径 `H1 > H2`；hash 去重；相邻块 shingle-Jaccard > 0.9 合并（无向量阶段的低成本相似度）。
- 禁区：不索引截图与密码、不索引被拒绝/失败的操作。

### 表结构（P3-2 定稿建议）

```
chunks(
  row_id INTEGER PRIMARY KEY AUTOINCREMENT,   -- FTS 用 rowid 关联，REPLACE 语义下更可控
  id TEXT UNIQUE,                             -- 业务 id（hash 派生）
  source_type, source_id,                     -- web_page | tool_result | local_file | skill
  conversation_id, task_id,                   -- A7：04 的「按会话收窄」靠这两列
  host, ordinal, text, char_text, tokens, hash,
  origin,                                     -- 硬要求：URL / 文件路径 / 消息 id
  title_path, created_at
)
chunks_fts_trigram: fts5(text,       content='chunks', content_rowid='rowid', tokenize='trigram')
chunks_fts_chars:   fts5(char_text,  content='chunks', content_rowid='rowid', tokenize='unicode61')
```

`char_text` 切分函数：CJK 字符之间插空格，拉丁/数字保持整词（实测样例 `机械键盘推荐 B站 评测` → `机 械 键 盘 推 荐 B 站 评 测`）。查询侧用同一函数切分后按 phrase 查询（`"键 盘"`）。

### P4-4 的两条守卫（不做会被误伤）

1. **仅当本次注入过片段才校验**（`context_meta.retrieved` 非空）。否则「1+1」这类无检索任务会被误标「部分完成」，直接把现有 10 用例打挂。
2. **origin 匹配用归一化**：去 scheme / `www.` / query，比对 host+path 前缀。模型常把 `https://search.bilibili.com/all?keyword=xxx` 写成 `bilibili.com`，严格全等会把正常引用判成未引用。

注入的每个片段记进 `context_meta.retrieved`，供回放与评估（04 原有要求）。禁止在没有 chunks 数据时假装检索成功。

### 12.3 实施中新发现并修掉的问题（原计划未列）

1. **FTS5 external content 的行标识列恒为 `rowid`**。`content_rowid='row_id'` 只是把 FTS 的 rowid 映射到 `chunks.row_id`；触发器里按内容表列名写 `(row_id, text)` 会直接报 `table chunks_fts_trigram has no column named row_id`。JOIN 同理必须写 `{table}.rowid`。
2. **查询整句当短语 → 预取永远 0 召回**。prepare 传的是整句任务目标，`MATCH '"整句话"'` 必然空。新增 `match_expression()`：trigram 按 3 字滑窗、字符级按相邻两词滑窗，各短语 `OR` 连接；短查询（≤12 字）额外保留整串。
3. **无真实出处的工具结果不入索引**。原实现给无名工具结果合成 `tool_result` 类 origin，会让模型检索到却无法署名 → 改为只认 url（`web_page`）与 path（`local_file`）。
4. **bigram Jaccard 的合并阈值**：重复文本的 distinct bigram 少、相似度天然偏低（实测 0.8），单测数据需「长而多变 + 极短差异」才能真正 >0.9。

## 本轮抽查证据

**抽样率**：3 项点名**全部复核**；另**追了 `_slot_client` 的密钥取值链到底**（这是本轮最重要发现）。

### A. ★ 最重要：4.9 的判据 ② 在「槽位换了一家 provider」这个场景下**不成立** —— 会拿到**主模型的 key**，造出必然 401 的客户端，而且**不告警**

**你 docstring 里判据 ② 是这么写的**：
> 「**拿不到密钥就不假装**：槽位换了一家 provider 但本机没有那家的钥匙时，**警告并退回主模型**，而不是造一个必然 401 的客户端。」

**但取值链的实际行为是这样**：
```python
# app/summaries.py::_slot_client
profile = providers.PROVIDERS.get(slot.provider)          # 槽位那家（例：openai）
key = providers.resolve_api_key(profile, self.settings)   # ↓ 看下面
if not key:
    log.warning("…没有该家的密钥…")                        # ← 只有 key 为空才走到
    return None
return ChatOpenAI(model=slot.model, base_url=…, api_key=SecretStr(key), …)

# app/providers.py::resolve_api_key
key = _secret_value(getattr(settings, "model_api_key", None))
if key:
    return key          # ← **第一步就返回，与 profile 无关！**
for name in profile.key_env_names: ...
return ""
```

**所以实际时序是**：

| 场景 | `settings.model_api_key`（主模型 key） | `resolve_api_key(openai, …)` 返回 | 结果 |
|---|---|---|---|
| 主模型是 deepseek，槽位配 openai | **deepseek 的 key（非空）** | **deepseek 的 key** | **`key` 非空 → 不告警 → 造客户端 → 拿 deepseek 的 key 打 openai 端点 → 必然 401** ❌ |
| 主模型是 deepseek，槽位也配 deepseek | deepseek 的 key | deepseek 的 key | ✅ 正确（同一家，key 本来就对） |
| 主模型没配 key（**测试里的情况**） | 空 | 走 `OPENAI_API_KEY` 环境变量 | ✅ 正确 |

**→ 判据 ② 声称处理的场景，恰恰是它没处理的场景。** 而且**比"拿不到密钥"更糟**：它**拿到了别人家的密钥**，所以 `if not key` 这道闸**根本不会触发**，`log.warning` **不会响**，客户端**照造不误**。

**为什么测试没抓到**（我核了 `_service`）：
```python
settings = Settings(data_dir=…, workspace=…, model="deepseek-chat")   # ← 不设 model_api_key
```
→ **测试里主模型永远没有 key** → `resolve_api_key` 的第一步恒为空 → 走环境变量分支 → **测试绿**。**危险场景从未被构造。**

**修法（最小改动，两层选一）**：

**① 在 `_slot_client` 里区分「是不是同一家」**：
```python
main_profile = providers.resolve_provider(self.settings)
if slot.provider == main_profile.id:
    key = providers.resolve_api_key(profile, self.settings)      # 同一家，主 key 就是它的
else:
    key = providers.resolve_key_for(profile)                     # 只查该家的 env / keyring 池
```
**② 或给 `resolve_api_key` 加一个 `provider_id` 前提**：只在 `profile.id == 主 provider` 时才信任 `settings.model_api_key`。

**并且补一条测试**：**主模型有 key + 槽位换一家 → 必须 `client is None` 且有警告**。**这条测试现在不存在，而它正好覆盖"槽位"这个功能的主要用法**（用户配槽位的目的就是换一家便宜的模型）。

### B. 你点名的 3 项

**① `_slot_client()` 的密钥来源是否合理 → ❌ 不合理，见 A 节；而且问题比"拿不到 key"更严重**

你说：「所以「槽位换了一家 provider 但 key 只存在 keyring 里」时，它会拿不到 key 而退回主模型。**这算不算没接完整？**」

**我的回答：算，而且实际行为不是"拿不到 key 而退回"，是"拿到了主模型的 key 而不退回"。**
- 你说的"拿不到 key"→ 只会发生在**主模型也没配 key** 的情况（罕见）

**这也让 4.9 的 ✅ 站不住**（见 ③）。

## 本轮抽查证据

**抽样率**：3 项点名**全部复核**；另**查了 `kanban_link` 的 Hermes 原始语义**（本轮最重要）。

### A. ★ 最重要：`link()` 是「接错概念」的**第 2 个实例**，而且这次**会破坏已有数据**

**你问的**：「我 `link()` 的实现是「**覆盖 parent**」而不是「**加一条边**」——**这是不是又一个「接错概念」？请核。**」

**我查了 Hermes 的实证** —— `02-tool-layer.md:389`：
> 「`kanban_link` | **两个已存在任务之间加父子依赖边** | `parent_id`, `child_id`, `board`」

`01-cli-surface.md:784`：
> 「`link` | **添加 parent→child 依赖** | `hermes kanban link [-h] parent_id child_id`」

**而 Orbit 的实现**（`kanban.py:348-383`）：
```python
def link(data_dir, child_id, parent_id) -> Card:
    """给两张**已存在**的卡**加一条父子依赖边**。      ← docstring 说"加一条边"
    ...
    card = by_id[child_id]
    card.parent = parent_id                          ← 实现是**单值赋值 = 覆盖**
```
**而模型是单值**：`kanban.py:79` `parent: str = ""`

**→ 所以是的，这是「接错概念」的第 2 个实例** ✓✓（第 1 个是第 41 轮的 `--source`）

**而且它比 `--source` 更糟 —— 它会破坏已有数据**：

| 操作序列 | Hermes | Orbit |
|---|---|---|
| `link(A → C)` | C 依赖 A | C.parent = A |
| `link(B → C)` | C 依赖 **A 和 B** | **C.parent = B**（**A 被静默抹掉**） |
| 后果 | 多依赖正确 | **依赖关系丢失，且不报错** |

**三个连带影响**：
1. **`claim()` 的闸门不完整** —— 它只查 `card.parent` 单链，**多依赖场景下会漏检**
2. **环检测只走单链** —— `kanban.py:381` `cursor = parent_card.parent`，**DAG 下需要全图 DFS**
3. **`blocked_by` 只报单条** —— 见 B②

**所以你的担心成立，而且比"没查 `depends_on`"更根本**：**不是"漏查了多依赖"，是"模型本身容不下多依赖"，而 docstring 声称"加一条边"。**

**两条路（必须选一条）**：

**① 改成真多依赖（对齐 Hermes）**
```python
parents: list[str] = []          # 替代 parent: str
# link(): card.parents.append(parent_id)（去重，不覆盖）
# 环检测：从 parent_id 全图 DFS 找 child_id
# claim(): all(by_id[p].status == DONE for p in card.parents)
# 迁移：parent → [parent] if parent else []
```
**代价**：动数据模型 + 迁移 + 三处调用点。**但这是唯一能让"多依赖"真正成立的改法。**

**② 保持单父，但把话说实**
- **改 docstring**：「Orbit 的卡是**单父**模型：`link()` 会**替换**已有的父卡，**不是追加**」
- **`link()` 的签名也改**（`child_id, parent_id` 保留，但语义写清是"设置"不是"添加"）
- **标 🟢（有意差异）** + 代价（「多依赖任务板做不到；需要多条依赖时只能靠人工拆分」）

**判据**：**签名对不代表语义对** —— `link(child_id, parent_id)` 的参数与 Hermes 一致，**但"加边"和"覆盖"是两件事**。

**我的倾向：选 ①** —— 因为**多依赖是任务板的常见需求**（"这张卡要等 A 和 B 都完成"），**而单父模型会让用户在第二次 `link` 时静默丢数据**，**那是"看起来能用、实际会坏"的最坏形状**。

### B. 你点名的另 2 项

**② `kanban_list` 的 `ready` 是否该考虑 `blocked` 状态 → ✅ `ready=False` 对，但 `blocked_by` 分不开两种原因**

**现状**（`kanban.py:577-578`）：
```python
"ready": card.status == STATUS_OPEN and not pending,
"blocked_by": pending,
```
- **`blocked` 的卡 → `status != OPEN` → `ready=False`** ✓ **正确**（不该被认领）
- **但 `blocked_by` 只含"未完成的父卡"** → **`blocked` 状态的原因在 `blocked_by` 里看不到**

**所以你的担心对**：**「blocked」和「等父卡」在 `ready` 上是同一个值（False），在 `blocked_by` 上只有后者有解释。**

**建议**：**`blocked_by` 里加一条显式原因**，让两种可分：
```python
"blocked_by": pending,                     # 等父卡
"blocked_reason": card.status == STATUS_BLOCKED and card.block_reason or "",
```
→ **这样 orchestrator 能区分"再等等"和"有人叫停"** —— 而**这两件事的处理完全不同**。

**③ `wait_status` 放宽是否掩盖真问题 → ⚠️ 我的根因假设是**假设**，不是实证；而且"放宽"不是"修好"**

**我上轮说的是**：「**根因假设**（我读了测试）：…`await wait_status(...)` 是真实任务 + 轮询等待 → 负载下窗口不够」——
**注意：那是假设，不是实证。** 我没有跑到"45s 内能过、15s 内不能过"的证据。

**所以你的担心是对的**：**如果你按一个假设改了，而假设是错的，那就是给真 bug 让路。**

**判据（我给的）**：
> **放宽超时是"容忍更慢的机器"，不是"修好根因"。**
> **45s 内能完成 → 假设成立；45s 仍失败 → 假设错了，要回去查任务为什么卡住。**

**建议补一条**（成本很低，价值很高）：**加"进度可观测"** —— 任务卡住时应该能看到**卡在哪一步**（最后一个事件、最后一次工具调用），而不是只有"超时"两个字。
**这样即使假设错了，下一次失败也能直接定位**，而不是又要猜一轮。

### B. 你点名要抽查的 3 项

**① `parent` 变成派生属性是否留了坑 → ⚠️ 有残留风险，但护栏该加在名字上，不是只在 docstring 里**

**现状**（`:96-102`）：
```python
@property
def parent(self) -> str:
    """**第一个前驱**（兼容旧读法）。

    只保留一个「主前驱」是为了不打破既有调用方（`summarize` / 测试），
    **但依赖判定一律走 `parents` 全集**——否则又多一条会漂移的路径。
    """
    return self.parents[0] if self.parents else ""
```

**docstring 写得对** ✓ —— 它说的是「**第一个前驱**」而不是「父卡」，**这个措辞是准确的**，而且明确划了"依赖判定走全集"。

**但你的担心成立**：「写清楚了不等于不会误用」✓ —— **具体误用有两种**：
1. **`if card.parent:`** 判"有没有依赖" → **有 3 个前驱时也返回真** → 这个其实没错
2. **`if card.parent == some_id:`** 判"是不是某个卡的子卡" → **只看第一个前驱** → **漏检其余** ✗ ← **这才是真风险**

**建议（按成本排）**：
| 方案 | 成本 | 效果 |
|---|---|---|
| **① 改名 `first_parent`** ⭐ | 一行 + 调用点 | **语义进名字，误用者一眼看见** |
| ② 加源码扫描断言（`app/` 里除 `parent` 定义处，不许出现 `.parent`） | 一条测试 | 挡新增误用 |
| ③ `len(parents) > 1` 时抛错 | 小 | **"我不知道返回哪个"比"随便返回一个"诚实** —— 但会打破 `summarize` |

**判据**：**兼容旧调用方 ≠ 允许旧语义。** `parent` 可以是"读一个前驱"的便捷方法，**但不能是"依赖判定"的入口** —— **而"第一个前驱"这个语义最好体现在名字里，而不是只在 docstring 里。**

**② 环检测只测了 A→B→A，没测分叉 → ✅ 该补，而且你补它的理由比"覆盖更多"更硬**

**关键洞察**：**`A→B→A` 这条用例在"单链游标"实现下也能测出来** —— 因为从 B 出发沿单链就能回到 A。**所以它不能证明 DFS 是对的**，它只证明了"环检测存在"。

**能区分 DFS 与单链的用例，必须是"环在第二个前驱上"**：
```
C.parents = [A, B]        ← C 有两个前驱
B.parents = [C]           ← 环在 B 这条上（C → B → C）
link(A → C)               ← 尝试给 C 再加一个前驱 A
```
- **单链游标**（只看 `parents[0] = A`）：A 无父 → **查不到环 → 漏检** ✗
- **全图 DFS**：走 A、B 两条 → **在 B 上发现 C → 报环** ✓

→ **所以这条用例才是 DFS 的证明。** **建议补它，而且测试名就写清"环在第二个前驱上"**，否则下一个人会以为 A→B→A 已经够了。

**③ `5.14` 的混合状态（52 已做 + 42 止损）怎么写才不误导 → 写"分子/分母 + 为什么停"，不要给整行一个状态**

**你的问题很准**：**一行里既有"已做 52 个"又有"42 条止损"，这是"一行一个状态"的局限。**

**但解法不是发明新状态，也不是拆行**（拆行会改分母，需口径变更日志）。**正确写法是把"状态"和"进度"分开**：

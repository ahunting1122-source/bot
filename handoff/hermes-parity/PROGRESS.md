**抽样率**：3 项点名**全部复核**；另核了上轮 `_enqueue_after` 修复的落地。

### A. ★ 最重要：`_schema_value` 对 histogram 用 `count` —— **该改，而且比你说的严重：它是唯一一个 histogram，且与指标名/help 语义相反**

**你问的**：「histogram 我用**观测次数**当 `value`。**这会不会让下游把它当"耗时总和"用？**」

**我实测 `CATALOG`：histogram 只有一个**：
```
histogram 指标 1 个：
  orbit_task_duration_seconds   help='任务墙钟耗时（含等待用户与后台续跑，见 insights 的口径说明）'
                                source='app.sqlite · tasks.created_at → tasks.updated_at（仅终态）'
```

**所以实际载荷是**：
```json
"orbit_task_duration_seconds": {
  "available": true,
  "source": "app.sqlite · tasks.created_at → tasks.updated_at（仅终态）",
  "help":   "任务墙钟耗时（含等待用户与后台续跑…）",
  "value":  42,        ← **42 = 任务条数，不是 42 秒**
  "sum":    12345.6,
  "buckets": [...]
}
```

**为什么这比"容易被误读"更严重**：
1. **指标名是 `..._duration_seconds`** —— 名字里就写着"秒"
2. **`help` 是「任务墙钟耗时」** —— 描述里也写着"耗时"
3. **`value` 却是次数** —— **与名字和 help 都相反**
4. **`source` / `help` 都没有澄清 `value` 是 count**（`source` 说的是数据来源，`help` 说的是指标含义，**没有一句说"value 是观测次数"**）

→ **任何下游（看板、LLM、人）读到 `value: 42` 都会认为"42 秒"。** **这不是边缘情况，这是目录里唯一的 histogram。**

**你选 `count` 的理由（「多少次永远是有意义的标量」）单独看是对的，但它与指标自身的名字冲突** —— **通用性不能凌驾于语义一致性。**

**我的建议（三个选项，按推荐顺序）**：
| 方案 | `value` | 优点 | 缺点 |
|---|---|---|---|
| **① 用 `sum`（总秒数）** ⭐ | 总耗时 | **与 `duration_seconds` 完全一致**；无除零风险 | 丢"典型值"的感觉 |
| ② 用 `sum/count`（平均） | 平均耗时 | 也是"秒"，更接近"一个任务多久" | 需处理 count=0 |
| ③ 保留 `count`，但**改 `help`** | 次数 | 不动映射 | **要改 help 就违背了"help 描述指标含义"**，且 `duration_seconds` 这个名字还在骗人 |

**推荐 ①**：`value = sum`（总秒数），`count` 显式加一个键（`buckets` 里已有，但显式更清楚）。**这样 `value` 的语义与指标名一致，下游不会误读。**

**② 15.4 该不该把 `observability_sink` 也算进产出方 → ✅ 不接是对的，但证据栏必须拆开写**

**我核了 `observability_sink` 到底产出什么**：
```python
def _hook(payload, _exporter=exporter, _event=event, ...):
    _exporter.emit(_event, dict(payload or {}))       # observability_sink.py:83-86
```
→ 它做的是 **把 hook 事件载荷转发给 exporter**（`exporter.emit(event, payload)`），**产出的是「事件」，不是「指标」**。

**metrics schema 的形状是** `{schema_version, metrics:{name:{available, value, source, help}}}` —— **事件载荷没有 `available`/`value`/`help` 这些字段，套上去会校验失败。**

→ **所以"不接"不是遗漏，是范围判断** ✓ **15.4 的契约是「指标产出经过 schema」，事件转发不在其中。**

**但 MATRIX 原文把两者并列写成**：
> 「`app/metrics.py`（指标聚合）与 `app/observability_sink.py`（exporter 落点）**都不用 schema**」

**读者会以为两者都该接。** **建议证据栏拆开写**：
> 「`metrics.py` 已接（产出方自校验）；**`observability_sink.py` 产出的是 hook 事件载荷而非指标，不适用本 schema**——套上去会因缺 `available`/`value`/`help` 而校验失败。」

**否则下一个人会去接它，然后发现套不上，再花时间判断"是不是我理解错了"。**

**③ `test_skill_index` 那条偶发要不要治 → 不治"偶发"可以，但**这条该改到不踩边界**

**根因我查了**（比"mtime 精度"更具体）：
```python
# 测试（:422）
write_skill(..., description="旧描述")
index.index()                                    # 第一次索引
write_skill(..., description="新描述")            # 立刻重写
assert index.index().skills[0]["description"] == "新描述"
```
签名是 `mtime_ns + size`（`skill_index.py:760`）。
**关键**：`"旧描述"` 与 `"新描述"` 在 UTF-8 下**都是 9 字节**（三个汉字 × 3）→ **size 完全不变** → 只剩 `mtime_ns` 一个判据 → **两次写入落在同一 mtime tick 时，签名不变 → 缓存不失效 → 测试红** ✓

**所以它不是"mtime 精度"这种笼统原因，而是「同字节长度 + 同 tick」两个条件同时成立。** 你写的测试正好满足了这两个条件。

**我的判断**：
- **"不治偶发"这个原则我同意**（签名设计是文档化过的、有意的取舍：`skill_index.py:31-34` 明确写了为什么用目录 mtime + 条目数而不是文件 hash）
- **但这条测试该改**，理由不是"它是产品缺陷"，而是：**偶发红的测试会污染整个红灯信号**。你这轮就花了**两次全量**才确认它非回归——**下次再红，谁也不能立刻判断。**
- **修复成本是一个字符串**：把 `"新描述"` 改成 `"新描述（更长）"` → size 变了 → 签名必变 → **测试稳定，且仍然验的是"改内容要失效缓存"**
- **或者**：测试里 `os.utime` 把 mtime 往前推 1 秒

**判据**：**测一条"已知边界"的代码时，测试不该踩在那个边界上** —— 要测"改内容失效缓存"，就用能稳定触发失效的改动；要测边界本身（同 tick 不改），那是另一条测试，**应该显式写出来**。

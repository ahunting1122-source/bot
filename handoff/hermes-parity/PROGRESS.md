**你的披露是**：
> 「Orbit 的 `open` 大致对应 Hermes 的 `todo`，**Hermes 那个更细的 `ready`（可认领）这一档 Orbit 没有单独建模**——**那是状态机的一档缺口，不是本函数的 bug。**」

**我核了状态机** —— `kanban.py:42`：
```python

```
`kanban.py:73-74`：
```python

```

→ **Orbit 的 `open` 明确是「可被认领」的** ✓

**而 Hermes 的分档是**（`01:795` / `02:385`）：
| Hermes | 可认领？ |
|---|---|
| `todo`（等依赖） | **不可** |
| `ready`（依赖已满足） | **可** |

**所以问题不是"少了一档状态"，而是**：

> **Orbit 把「等依赖」和「可开工」合并进 `open`，而 `open` 是可认领的** →
> **`unblock` 把卡放回 `open`（父卡未 done）后，那张卡仍然能被认领** →
> **你原本担心的死循环（认领 → 又卡在同一依赖 → 再 block → 再 unblock）回来了。**

**而 `[dependency]` 评论不阻止认领** —— `kanban.py:310` 那条评论是**记录**，不是**闸门**。

**所以修复只关了一半**：
| 问题 | 你的修复 | 状态 |
|---|---|---|
| **死胡同**（拒绝 → 用户无路可走） | 改成放回 `open` | ✅ **关掉了** |
| **死循环**（可认领 → 又卡住） | `[dependency]` 评论 | ❌ **没关掉** |

**修法（两个，② 更便宜）**：

**① 加 `ready` 档（Hermes 的做法）**
`open`（等依赖，不可认领）→ `ready`（依赖满足，可认领）→ `doing` → `done`
**代价**：多一档状态 + 所有状态判断处要区分 `open`/`ready`。

**② 在认领路径上加闸（推荐，改动小）**
```python
def claim(data_dir, card_id, who) -> Card:
    card = _load_card(...)
    parents = [c for c in _all(data_dir) if c.id in card.parents]
    unfinished = [p for p in parents if p.status != "done"]
    if unfinished:
        raise KanbanError(f"父卡未完成（{unfinished[0].id} 仍是 {unfinished[0].status}）："
                          f"先完成依赖再认领")
    ...
```
→ **效果与加 `ready` 档相同**（等依赖的卡认领不了），**但不动状态机** ✓
**而且它把闸门放在了"真正发生危害的地方"** —— 危害是"认领"，不是"状态值"。

**判据**：**闸门要放在危害发生的那一步，不是放在看起来相关的字段上。**（这与第 34 轮 `_slot_client` 的"闸门位置错了"同族）

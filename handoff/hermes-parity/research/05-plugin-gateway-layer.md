**Python 命名空间**：插件被加载为 `hermes_plugins.<name>` 包。
证据：`_internal\tools\registry.py` 中 `deregister()` 的所有权检查注释：

> "Ownership check: bind to the plugin package root (``hermes_plugins.{name}``), not the exact module string.
> A handler defined in ``hermes_plugins.pkg.handlers`` is still owned by the ``hermes_plugins.pkg`` package"

**发现机制**：`kind` 决定"自动加载"还是"显式启用"。
证据：`plugins\web\__init__.py` 注释——

> "They auto-load via `kind: backend` and register via `ctx.register_web_search_provider()` into `agent.web_search_registry`."

而 `plugins\platforms\a2a\plugin.yaml` 的 `provides_tools` 注释给出了另一条关键规则：

> "Declaring them here is what asks discovery to import `tools.py` in CLI/TUI processes, where the plugin is
> otherwise deferred and the tools would never register at all (#78050). The inbound adapter stays deferred
> either way — only this submodule is imported."

即：**插件默认是"延迟（deferred）"的**，只有 `kind: backend` 类、或显式声明 `provides_tools`
（要求发现期就 import）的插件才会在 CLI/TUI 进程里立刻注册。

#### 1.2.1 `requires_env` / `optional_env` 元素 schema

共 168 条声明。两种写法并存，**必须都支持**：

**写法 A — 裸字符串**（用于已知变量名、无 UI 提示需求的场景）：

  - FAL_KEY                       # image_gen\fal

optional_env:
  - name: RAFT_PROFILE

### 1.3 发现 / 加载 / 启用 / 禁用

#### 1.3.1 `config.yaml` 的 `plugins` 段（本机真实样本）

证据：`E:\Hermes Agent CN Desktop\data\hermes-home\config.yaml`

```yaml
plugins:
  enabled:
    - superpowers/.hermes-plugin      # 路径式 key：<owner>/<repo> 或本地相对路径
  disabled: []
  entries:
    superpowers/.hermes-plugin:
      allow_tool_override: false      # 授权位：是否允许该插件覆盖内置工具
```

三段语义：

| 键 | 类型 | 语义 |
|---|---|---|
| `plugins.enabled` | list[str] | 启用白名单。key 是**插件 id / 路径**（`superpowers/.hermes-plugin` 这种带斜杠的写法说明 bundled 与 user 插件共用同一 key 空间）。 |
| `plugins.disabled` | list[str] | 显式禁用（优先级高于 `enabled`；`hermes plugins install` 装"可移植包"时默认落这里——见 `plugins install --no-enable`）。 |
| `plugins.entries.<key>` | dict | 每插件细粒度授权。目前唯一子键 `allow_tool_override: bool`。 |

#### 1.3.2 `allow_tool_override` —— 唯一的内置工具覆盖授权位

这是插件隔离里最重要的一条硬约束。证据：`_internal\tools\registry.py`：

* 内部结构：`self._plugin_override_policy: Dict[tuple[Optional[str], str], _PluginOverridePolicy]`
  —— 键是 `(profile_scope, plugin_module)`，值是带身份的授权记录 `_PluginOverridePolicy(allowed: bool)`。
  注释："Identity-bearing authorization record for one plugin generation."
* 拒绝时的错误文案（原样摘录）：

```
Tool deregistration REJECTED: plugin %r attempted to remove tool %r (toolset %r)
it does not own, without operator opt-in.
Set plugins.entries.%s.allow_tool_override: true in config.yaml to allow it.
```

* 抛出的异常：`PermissionError: Plugin module {caller_mod!r} cannot deregister tool {name!r}
  (toolset {entry.toolset!r}) without operator opt-in (allow_tool_override).`
* `deregister()` 也被同一策略保护，理由注释：

> "Gated by the same operator opt-in policy `register(override=True)` enforces. Without this, a plugin could
> bypass that gate entirely by deregistering a tool it doesn't own and then calling plain `register()` over
> the now-empty slot — `register()` only runs its override check when an `existing` entry is present, so
> removing it first skips the check altogether."

* MCP 工具集（`mcp-*`）豁免此策略（动态发现需要 nuke-and-repave）。
* 卸载时的回滚：`restore_registration(name, current, previous, scope=...)`，用**身份比较**
  （`if target.get(name) is not current: return False`）保证"卸载本插件的覆盖"不会误删后来者的更新注册。

CLI 侧对应开关：`hermes plugins enable --allow-tool-override` / `--no-allow-tool-override`
（见 §4.8）。

### 1.4 `plugin_storage.py` 与 `plugin_utils.py`

#### 1.4.1 `plugin_storage.py`（2998 B）—— 持久化约定

**它解决的问题**（原文摘录，这段是设计意图的最佳证据）：

> "Plugins that want durable state today invent their own paths, and most of them invent the same wrong one:
> a scratch directory inside `<hermes home>/plugins/<name>/`. That tree is the plugin *install* dir —
> `hermes plugins remove` deletes it and `hermes plugins update` git-pulls into it — so user data parked
> there dies with the code that wrote it."

**导出 API**（`__all__ = ["plugin_data_dir", "plugin_db"]`）：

| 函数 | 签名 | 行为 |
|---|---|---|
| `plugin_data_dir(name)` | `-> Path` | 返回并 `mkdir -p` `<hermes home>/plugin-data/<name>/`。**不受 install/update/remove 影响**；每次调用都经 `hermes_constants.get_hermes_home()` 解析，因此**跟随 profile 切换**（注释明确："Don't cache the result across profile switches."）。 |
| `plugin_db(name, filename="data.db")` | `-> sqlite3.Connection` | 打开 `<data dir>/<filename>`，设 `PRAGMA journal_mode=WAL`（"so a dashboard reader and an agent-tool writer can coexist"）+ `PRAGMA foreign_keys=ON`，`check_same_thread=False`（适配 FastAPI/工具多线程）。**事务纪律仍由调用方负责**。 |

**安全校验**：

* `_NAME_RE = ^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`，且额外拒绝含 `..` 的名字
  —— 注释："Anything else could escape the data root via separators or traversal."
* `plugin_db` 的 `filename` 必须满足 `Path(filename).name == filename`（禁止路径穿越）。
* **密钥不入此约定**：原文 "Secrets are deliberately NOT part of this convention — credential reads go
  through `agent.secret_scope` / `.env` like everywhere else in Hermes."

#### 1.4.2 `plugin_utils.py`（4640 B）—— 线程安全单例原语

**它解决的问题**：插件作者最常踩的"懒加载单例 TOCTOU"。原文：

> "When two threads call `get_client()` before the singleton is set, both pass the `is not None` guard,
> both run the expensive initialization, and the second write clobbers the first — leaking whatever resource
> the first client opened (connections, file handles, background threads).
> Multi-threaded agent sessions share one process (delegated tool calls, background workers, the
> self-improvement fork), so this race is reachable in practice."

**导出 API**（`__all__ = ["lazy_singleton", "SingletonSlot"]`）：

| 符号 | 签名 | 行为 |
|---|---|---|
| `lazy_singleton(factory)` | 装饰器 `Callable[[], T] -> Callable[[], T]` | 双检锁包装零参工厂。工厂**只跑一次**；附带 `.reset()` 用于测试/拆除。工厂抛异常时不缓存，下次重试（锁两种情况都会释放）。 |
| `SingletonSlot[T]` | class | 手工槽位，用于"accessor 带配置参数"的场景。`get(factory)`（首次成功构建后缓存，**后续忽略参数**——"first config wins"）、`peek()`（不构建、只看缓存）、`reset()`。用 `__slots__ = ("_lock","_value","_set")`。 |

两者都只依赖 stdlib `threading`（"import-light … so any plugin can import them without dragging in
heavyweight host modules"）。

### 1.6 插件隔离与 `plugin_guard.py` 的约束

隔离是**三层**，各层强度不同，必须分清：

#### 层 1：进程内，无沙箱（最弱但最真实）

证据：`tools\plugin_guard.py` 开篇原文——

> "Plugins are strictly more dangerous than skills — they run Python **in-process with the agent** — but they
> are also *expected* to do things a skill never should: read their own API keys from environment variables
> (the documented `requires_env` pattern), call provider HTTP APIs with those keys, and spawn subprocesses."

结论：插件代码与 agent 同进程、同权限。**没有 Python 级沙箱**。隔离只能靠"安装期扫描 + 授权位 + 作用域"。

#### 层 2：profile 作用域（进程内隔离）

证据：`tools\registry.py` 的 `ToolRegistry`：

* `self._tools`（进程全局内置）vs `self._scoped_tools: Dict[str, Dict[str, ToolEntry]]`（**按
  `HERMES_HOME` 解析出的 profile key 分层的插件覆盖层**）。
* `_merged_tools(scope)`：`merged = dict(self._tools); merged.update(self._scoped_tools.get(active_scope, {}))`
  —— profile 先看自己的 overlay，再看全局内置。
* 越界防护（`deregister` 原文）：
  `Scoped plugin module {caller_mod!r} cannot deregister process-global tool {name!r}; register a scoped override instead.`
* 作用域记录**在策略移除后仍保留**：`_plugin_module_scopes` 注释
  "Scope attribution stays durable after policy removal so delayed code remains confined to the profile where its module was loaded."
* 多 profile 进程里 `check_fn` 缓存也按 profile 分键（`check_fn_cache_scope()`），无法解析 profile 身份时
  **fail closed**（`CHECK_FN_CACHE_BYPASS` 绕过缓存直接探测）。

#### 层 3：`plugin_guard.py`（12310 B）—— 安装/更新期静态扫描闸

位置：`_internal\tools\plugin_guard.py`（**在 `tools/` 下，不在 `plugins/` 下**）。
定位原文：

> "Hermes already scans hub-installed *skills* via `tools/skills_guard.py`; this module extends the same
> static-analysis engine to `hermes plugins install` and `hermes plugins update`, which previously cloned and
> executed arbitrary Git repositories unscanned."

**扫描策略**（复用 `tools.skills_guard` 引擎，做插件化改造）：

| 维度 | 规则 |
|---|---|
| 扫描范围 | 全树（排除 `EXCLUDED_DIRS = {.git, __pycache__, node_modules, .venv, venv, .mypy_cache, .pytest_cache, .ruff_cache, .tox}`） |
| 文档/配置文件 | 跑**完整** skills_guard 威胁模式集（README、after-install.md、plugin.yaml…）——"where prompt-injection and social-engineering content lives" |
| 代码文件 | 对 `CODE_FILE_EXTENSIONS = {.py,.js,.ts,.sh,.bash,.rb,.pl,.php}` **豁免** `CODE_EXEMPT_PATTERN_IDS`（15 个模式）：`python_environ_get_secret` / `python_getenv_secret` / `python_os_environ` / `node_process_env` / `ruby_env_secret` / `env_exfil_{httpx,requests,fetch,curl,wget}` / `context_exfil` / `send_to_url` / `fake_policy` / `agent_config_mod` / `agent_config_contract` / `encoded_exfil` |
| 仍然拦截（代码文件也不豁免） | 外部凭证库访问（`~/.ssh`、`~/.aws`、`~/.hermes/.env` 的**读取**）、反弹 shell、破坏性命令、持久化机制、混淆执行、已知外泄服务 |
| 严重度重映射 `SEVERITY_REMAP` | `binary_file: critical→high`、`hermes_env_access: →medium`（"a reference is informational"；**真读**文件仍触发 `read_secrets_file` critical）、`curl_pipe_shell: →high` |
| 结构限额 | `MAX_PLUGIN_FILE_COUNT=400`、`MAX_PLUGIN_TOTAL_SIZE_KB=10*1024`、`MAX_PLUGIN_SINGLE_FILE_KB=1024` |
| 结构检查 | 符号链接逃逸（`symlink_escape` critical）/ 断链（`broken_symlink` medium）/ 超大单文件 / 可疑二进制扩展 / 文件数超限 / 总量超限 |

**三级裁决 → 安装策略**（`should_allow_plugin_install(result, force)`，返回 `(allowed, reason)`）：

| verdict | `allowed` | 行为 |
|---|---|---|
| `safe` | `True` | 正常安装（"Allowed (clean scan)"） |
| `caution` | `None`（或 `True` if `--force`） | 需要显式确认：交互提示 / `--force` / 调用方 decision 回调 |
| `dangerous` | `False` | **阻断，且 `--force` 不覆盖** —— 原文："`--force` does NOT override a dangerous verdict." |

其他：`PLUGIN_SCANNER_VERSION = "plugin-guard-v1"`；所有外部装插件一律 `trust_level="community"`；
结果带 `scan_provenance = {scanner_version, verdict, source}`（可审计溯源）。
导出面：`scan_plugin` / `should_allow_plugin_install` / `format_scan_report` / `PLUGIN_SCANNER_VERSION`。

#### `plugin_api.py` 契约

证据（`kanban\dashboard\plugin_api.py` 模块 docstring）：

> "Kanban dashboard plugin — backend API routes.
> **Mounted at `/api/plugins/kanban/` by the dashboard plugin system.**
> This layer is intentionally thin: every handler is a small wrapper around `hermes_cli.kanban_db` or a direct
> SQL query. Writes use the same code paths the CLI and gateway `/kanban` command use, so the three surfaces
> cannot drift."

硬契约：

1. **必须暴露模块级 `router = APIRouter()`**（两例均 `from fastapi import APIRouter; router = APIRouter()`）。
   dashboard 负责把它挂到 `/api/plugins/<manifest.name>/`。
2. **必须能在"无 dashboard 依赖"下 import**（供单测）。
   `hermes-achievements\dashboard\plugin_api.py` 的写法：

```python
try:
    from fastapi import APIRouter
except Exception:  # Allows local unit tests without dashboard dependencies.
    class APIRouter:  # type: ignore
        def get(self, *_args, **_kwargs): return lambda fn: fn
        def post(self, *_args, **_kwargs): return lambda fn: fn
```

   同理 `get_hermes_home()` 也有 `ImportError` 兜底（回退读 `HERMES_HOME` 或 `~/.hermes`）。
3. **认证由 dashboard 中间件统一施加，插件不得自带例外**。原文：

> "Plugin HTTP routes go through the dashboard's session-token auth middleware (`web_server.auth_middleware`)
> just like core API routes — every `/api/plugins/...` request must present the session bearer token (or the
> session cookie set when you load the dashboard HTML). The token is the random per-process `_SESSION_TOKEN`
> printed at startup; the dashboard's own pages inject it via `window.__HERMES_SESSION_TOKEN__`."

4. **WebSocket 认证走统一闸门**，用 `?token=` query 参数（"browsers cannot set the Authorization header on
   an upgrade request"）。且 `kanban` 已从"只认 `_SESSION_TOKEN`"改为委托
   `hermes_cli.web_server._ws_auth_ok`，以同时支持三种模式：

| 模式 | WS 凭证 |
|---|---|
| loopback / `--insecure` | 旧式 `?token=<_SESSION_TOKEN>` |
| gated OAuth | 单次性 `?ticket=`（浏览器 SDK `buildWsUrl` 每次连接新铸） |
| server-internal | 进程生命期 `?internal=` |

   注释点明了这样改的原因："The previous bespoke check only understood `_SESSION_TOKEN`, so the kanban
   live-events WS was rejected on every OAuth-gated deployment even though the rest of the dashboard worked."

5. **实时推送模式**：`/events` WebSocket 短轮询 tail 追加型 `task_events` 表
   （"WAL mode lets reads run alongside the dispatcher's IMMEDIATE write transactions"）。

> `hermes dashboard --host 0.0.0.0` 之所以可接受：原文
> "plugin routes are no longer an unauthenticated exception. The auth still isn't multi-user — anyone who can
> read the printed URL+token gets full dashboard access — but they can't ride along just because they can
> reach the port."

**通用契约**（`_internal\gateway\platforms\ADDING_A_PLATFORM.md`，插件路径）：

## 3. Gateway 机制

### 3.1 进程模型与三个状态文件

Gateway 是一个**独立的长期驻留 dispatcher 进程**，与 CLI 会话分离。它会：
接收各平台入站消息 → 路由到 `SessionSource` → 拉起 agent turn → 把回复经适配器发出。

`gateway run` 的帮助文本暴露了进程模型的硬约束：

> "`--force` Start a foreground gateway even when a systemd/launchd/s6 service already supervises this
> profile. **Without `--force`, the command refuses because a second dispatcher escapes the service and can
> corrupt shared gateway state.**"

即：**同一 profile 只允许一个 dispatcher**。这是"共享 gateway 状态"（下面三个文件 + 会话/配对/目录）的
写入一致性前提。

#### 3.1.1 `gateway-starts.log` — 启动时间戳序列（崩溃循环检测）

本机真实内容（`E:\Hermes Agent CN Desktop\data\hermes-home\gateway-starts.log`，716 B，39 行）：

```
1786276028.148717
1786276229.010939
1786276372.538203
...
1788781898.32934
```

* **结构**：纯文本，每行一个 Unix epoch 浮点秒（启动时刻），**追加写**，无表头。
* **含义**：每次 gateway 启动追加一行。用于**崩溃循环（crash-loop）检测与重启退避**——
  短时间内密集的启动戳说明进程在反复崩溃重启（本机样本里 `1786408xxx`–`1786409xxx` 区间
  有 ~10 次启动集中在约 30 分钟内，是典型的反复重启痕迹）。
* `[推断]` 消费方：`hermes gateway start/restart` 的 stale-process 清理与退避逻辑；
  `gateway status --deep` 的"反复重启"诊断。

#### 3.1.2 `processes.json` — 后台进程登记簿（`terminal(background=true)` 的落盘快照）

本机真实内容（2657 B，3 条记录）。结构 = **JSON 数组**，每条一个被托管的后台进程：

```json
{
  "session_id": "proc_130747721a0f",     // 进程 id（proc_ + 12 hex）
  "command": "cd /e/bbbooottt/backend && uv run uvicorn app.main:app --host 127.0.0.1 --port 6185",
  "pid": 24768,
  "pid_scope": "host",                    // host = 宿主 PID 命名空间（非容器内）
  "host_start_time": 179276178128,        // 宿主进程创建时间（防 PID 复用）
  "systemd_unit": "",                     // 若由 systemd 托管则填 unit 名
  "cwd": "E:\\bbbooottt\\backend",
  "started_at": 1792761781.1879017,       // epoch 秒
  "task_id": "session:20261023_210715_c67dfb",
  "owner_task_id": "20261023_210715_c67dfb",
  "session_key": "20261023_210715_c67dfb",
  "watcher_platform": "",                 // 输出匹配时的通知目标（平台）
  "watcher_chat_id": "",
  "watcher_user_id": "",
  "watcher_user_name": "",
  "watcher_thread_id": "",
  "watcher_message_id": "",
  "watcher_interval": 0,
  "parent_session_id": "",
  "notify_on_complete": false,
  "watch_patterns": ["Uvicorn running","Application startup complete","Error","Traceback"]
}
```

**含义**（源码证据：`_internal\tools\process_registry.py` docstring）：

> "Process Registry -- In-memory registry for managed background processes.
> Tracks processes spawned via `terminal(background=true)`, providing:
> - Output buffering (rolling 200KB window)
> - Status polling and log retrieval
> - Blocking wait with interrupt support
> - Process killing
> - **Crash recovery via JSON checkpoint file**
> - **Session-scoped tracking for gateway reset protection**"

即 `processes.json` 就是那个 "JSON checkpoint file"。字段族语义：

| 字段族 | 作用 |
|---|---|
| `session_id` / `pid` / `pid_scope` / `host_start_time` | 进程身份（`host_start_time` 与 pid 一起构成**防 PID 复用**的稳定身份） |
| `task_id` / `owner_task_id` / `session_key` / `parent_session_id` | 归属：哪个会话/任务起的，用于**会话作用域**与 gateway reset 保护 |
| `watcher_*` + `watch_patterns` + `watcher_interval` + `notify_on_complete` | **输出守望**：命中 `watch_patterns` 时往 `watcher_platform:watcher_chat_id`（可选 `thread_id`/`message_id`）推送通知 |
| `systemd_unit` | 由 systemd 托管时记录 unit 名，便于统一 kill |
| `cwd` / `command` / `started_at` | 复现与审计 |

> 注意区分：`processes.json` 记的是 **agent 工具起的后台进程**（uvicorn、doubao2api 等），
> 不是 gateway 自身进程。

#### 3.1.3 `spawn-ledger.json` — 机器级 spawn 账本（孤儿回收）

本机真实内容（454 B，1 条）：

```json
[{
  "pid": 9472,
  "create_time": 1793078582.022341,   // 宿主进程创建时间（PID 复用防护）
  "purpose": "dashboard",             // 生成目的标签
  "install": "c79db19ee0ea",          // 安装实例 id（多版本共存时区分）
  "spawner_pid": null,
  "spawner_create": null,
  "registered_at": 1793078585.351421,
  "argv": "E:\\Hermes Agent CN Desktop\\data\\versions\\0.21.0-cn.18\\hermes-agent-cn-runtime-win32-x64.exe dashboard --host 127.0.0.1 --port 9120 --no-open",
  "host": "127.0.0.1",
  "port": 9120,
  "profile": ""
}]
```

**含义**（源码证据：`_internal\tools\mcp_tool.py` 的 `register_child` 调用点注释）：

> "Positive identity for the machine spawn ledger (#61514): record each helper child as
> `(pid, create_time, '<purpose>', spawner=this process)` so **startup sweeps can reap orphans left after an
> unclean parent exit**. Best-effort — never let ledger I/O break MCP startup."

源码调用：`from hermes_cli.process_identity import register_child; register_child(_pid, "mcp-helper")`。

语义要点：

* **机器级（machine-wide）**，不按 profile 隔离 —— 它记录的是"这台机器上有哪些 Hermes 帮忙起的子进程"。
* 身份三元组 `(pid, create_time, purpose)`，`spawner_pid`/`spawner_create` 记录父子关系。
* 用途：**启动期扫除（startup sweep）**——父进程异常退出（被 kill、蓝屏、断电）后，
  下次启动能凭 `create_time` 精确识别并回收孤儿进程，而不会因 PID 复用误杀无关进程。
* 已知 `purpose` 取值：`dashboard`、`mcp-helper`（`[推断]` 还可能有 gateway-restart-watch 等）。
* 与 `processes.json` 的分工：`processes.json` = **agent 工具起的任务型后台进程**（有 watcher/会话归属）；
  `spawn-ledger.json` = **Hermes 自身起的辅助子进程**（dashboard、MCP helper），只管回收。

### 3.3 Pairing（DM 配对授权码）

**语义**：陌生人第一次 DM bot 时，bot 不直接服务，而是**回一个配对码**；管理员在宿主侧批准后该用户才被授权。

### 3.5 Peer（跨机器 bot 间 DM）

**语义**：把**另一台机器上的 Hermes gateway** 注册成本机的一个 peer，然后本机 agent 可以
直接给那边的 agent 发消息并拿到回复——这是 `hermes -p <bot> chat` 的**跨机孪生**。

CLI（`hermes peer --help`）帮助文本原文：

> "Register other Hermes gateways as peers and message their agents. `hermes peer dm <peer>[/<agent>] "..."`
> delivers into the remote agent's **canonical Bot Chat** over the peer's API server and prints the reply —
> the cross-machine twin of `hermes -p <bot> chat`. **The peer must run the `api_server` platform; its
> `API_SERVER_KEY` is stored locally as a credential in `~/.hermes/.env`.**"

| 子命令 | 参数/选项 | 语义 |
|---|---|---|
| `peer add`（别名 `set`） | `<name>`（小写 slug）`--url URL`（必需，如 `http://spark.lan:8377`）`--key KEY`（对端 `API_SERVER_KEY`）`--note NOTE` | 注册或更新 peer |
| `peer list`（`ls`） | — | 列已注册 peer |
| `peer remove`（`rm`） | `<name>` | 删除 |
| `peer dm` | `<peer>[/<agent>]` `[message]`（省略则读 stdin）`--json` | **同步**发一条并打印回复 |
| `peer run` | 同上 + `--idempotency-key`（省略则自动生成） | **异步**起一个长 turn，立刻返回 run ID |
| `peer status` | `<peer>[/<agent>]` `<run_id>` `--json` | 读异步 run 的状态与最终输出 |
| `peer stop` | `<peer>[/<agent>]` `<run_id>` `--json` | 停掉**单个**异步 run，不影响其他 turn |

**退出码契约**（原文）：`0` ok / `1` 投递或 peer 错误 / `2` 用法错误。

**示例**（原文）：

```
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer dm spark "Message from 🤖 dixie (@dixie): disk status?"
hermes peer dm spark/researcher "..."   # named profile on a multiplexed peer
hermes peer run spark --idempotency-key ticket-123 < long-task.txt
hermes peer status spark run_abc123
```

关键点：`<peer>/<agent>` 语法支持**多路复用 peer**上的具名 profile。

### 3.6 Send（脚本发消息，无需网关在线）

CLI（`hermes send --help`）帮助文本原文：

> "Pipe text from any shell script to any messaging platform Hermes is already configured for. **Reuses the
> gateway's platform credentials (`~/.hermes/.env` + `~/.hermes/config.yaml`) — no LLM, no agent loop, no
> running gateway required** for bot-token platforms like Telegram/Discord/Slack/Signal."

| 选项 | 语义 |
|---|---|
| `[message]`（位置） | 消息正文。省略则读 `--file` 或 stdin |
| `-t, --to TARGET` | 投递目标。格式：`platform`（home channel）/ `platform:chat_id` / `platform:chat_id:thread_id` / `platform:#channel-name` |
| `-f, --file PATH` | 从文件读正文（纯文本）。`-` 强制 stdin。**发图片/文件请用消息体里的 `MEDIA:<path>`** |

**目标语法实现细节**（源码证据：`tools\send_message_tool.py` 的正则常量）——
这是 parity 必须逐条对齐的：

| 平台 | 目标形态 | 正则/规则 |
|---|---|---|
| Telegram / Discord | `-?\d+(:thread)?` | `_TELEGRAM_TOPIC_TARGET_RE = ^\s*(-?\d+)(?::(\d+))?\s*$`（Discord snowflake 复用同一正则，`_NUMERIC_TOPIC_RE`） |
| Feishu | `oc_/ou_/on_/chat_/open_` 前缀 | `^\s*((?:oc\|ou\|on\|chat\|open)_[-A-Za-z0-9]+)(?::([-A-Za-z0-9_]+))?\s*$` |
| Slack | 会话 ID `[CGD][A-Z0-9]{8,}` | `_SLACK_TARGET_RE`；另有 `_SLACK_USER_ID_RE`（`U...` → 先 `conversations.open` 换 `D...`）、`_SLACK_USER_NAME_RE`（`@handle` → 先 `users.list` 解析）、`_SLACK_MENTION_RE`（`<@U...>`）、`_SLACK_THREAD_TARGET_RE`（`<conversation_id>:<thread_ts>`） |
| 微信 | `wxid_`/`gh_`/`v\d+`/`wm`/`wb` 前缀，`@chatroom` 后缀，`filehelper` | `_WEIXIN_TARGET_RE` |
| 元宝 | `group:` / `direct:` 前缀 | `_YUANBAO_TARGET_RE` |
| 电话类（photon/signal/sms/whatsapp） | E.164 `+<7..15 位数字>` | `_PHONE_PLATFORMS = frozenset({"photon","signal","sms","whatsapp"})` + `_E164_TARGET_RE` |
| Photon | DM GUID `any;-;+<6+ 位>` | `_PHOTON_DM_GUID_RE` |
| WhatsApp | JID：`@g.us` / `@s.whatsapp.net` / `@lid` / `@broadcast` / `@newsletter` | `_WHATSAPP_JID_RE`（大小写不敏感） |
| Buzz | 原生 UUID | `_BUZZ_UUID_RE` |
| Email | 裸邮箱地址 | `_EMAIL_TARGET_RE`（避免落到"频道名解析"分支） |

home channel 环境变量名有例外映射：
`_HOME_CHANNEL_ENV_OVERRIDES = {"email": "EMAIL_HOME_ADDRESS"}`（email 不读 `EMAIL_HOME_CHANNEL`）。

### 3.8 Pause / Resume（紧急停止语义）

CLI（`hermes pause --help` / `hermes resume --help`）帮助文本原文：

> `pause`: "Engage the global emergency stop. **Halts NEW work only — cron dispatch, kanban dispatch, and
> new gateway turns — until `hermes resume`. In-flight work is never killed.**"
> `--reason REASON`: "Optional reason stored in the sentinel and shown to users"
>
> `resume`: "**Remove the ESTOP sentinel**; dispatch resumes on the next tick."

精确语义表：

| 维度 | 行为 |
|---|---|
| 实现机制 | **ESTOP 哨兵文件**（sentinel）。`pause` 写入、`resume` 删除 |
| 拦截范围 | ① cron 派发 ② kanban 派发 ③ **新的** gateway turn |
| **不**拦截 | 已在执行中的工作（"In-flight work is never killed"） |
| 生效时机 | `pause` 立即（新 turn 拒绝）；`resume` 在**下一个 tick** 恢复派发 |
| 审计 | `--reason` 文本存进哨兵并展示给用户 |
| 作用域 | "global" —— 全局，跨 profile |

> 这是**软熔断**而非 kill switch：它挡的是"新工作入口"，不是运行中的进程。
> 要真正杀进程需要 `gateway stop` / `job_kill` / `process_registry.kill`。

## 6. Orbit 必须补齐的 Top 6

> 判定标准：Hermes 已形成**稳定契约**（有 schema / 有源码注释钉死 / 有 CLI 面）、
> 且 Orbit 若缺失会导致**第三方无法接入**或**运维无法观测**的项。按"缺失代价 × 接入摩擦"排序。

### 1️⃣ `plugin.yaml` 声明式 manifest（16 字段 schema + 富字典 env）
**为什么必须补**：这是全部 103 个插件、22 个平台的**唯一统一入口**。缺它就没有声明式安装/配置/文档。
必须包含：`name`/`version`/`description`/`author`/`kind`（4 值枚举决定加载时机）/
`requires_env`+`optional_env`（**必须同时支持裸字符串与富字典 6 子字段** `name`/`description`/`prompt`/
`password`/`url`/`category`）/`label`/`hooks`/`provides_*`（tools/web/browser）/`pip_dependencies`/
`external_dependencies`（`name`/`install`/`check`）/`platforms`/`homepage`。
**Hermes 的隐性契约**：`requires_env` 会自动注入 setup 向导的 `OPTIONAL_ENV_VARS`；
`provides_tools` 会改变发现期 import 时机。这两条不实现，声明就是死的。

### 2️⃣ `ctx.register_*` 能力注入面（19 种）+ 17 个 hook 事件
**为什么必须补**：这是插件"能做什么"的完整边界。Orbit 若只提供"注册工具"一种，就挡死了
provider 生态。必须覆盖 **13 种 bundled 插件真实调用**：`register_hook`(38) / `register_platform`(24) /
`register_web_search_provider`(9) / `register_memory_provider`(8) / `register_image_gen_provider`(7) /
`register_dashboard_auth_provider`(4) / `register_cli_command`(4) / `register_tool`(3) /
`register_video_gen_provider`(3) / `register_browser_provider`(3) / `register_middleware`(2,
`llm_execution`+`tool_execution`) / `register_command`(2) / `register_cron_scheduler`(1)；
外加 **3 种平台扩展点**（`register_platform_handler` / `register_slack_action_handler` /
`register_telegram_handler`——bundled 插件零调用但 15 个适配器都在等它，是第三方平台插件的唯一入口）
与 **3 种文档化 API**（`register_skill` / `register_auxiliary_task` / `register_context_engine`）。
配套 **17 个 hook 事件**（§1.5.2）——注意 `transform_tool_result` 与 `on_pre_compress` 各只有 1 个
使用者，极易漏掉，但它们是"非阻塞安全提示"和"压缩前落盘"的**唯一**挂点。
**统计陷阱**：按字符串出现次数统计会把 `register_platform_handler` 虚高到 15（13 处是注释），
Orbit 的对齐验收必须用"真实调用点"口径。

### 3️⃣ 平台适配器基类契约（22 适配器 / 7 必选 + 5 可选方法 + 5 边缘 hook）
**为什么必须补**：Hermes 的 22 个平台之所以能"零改核心接入"，靠的就是这套基类契约。
Orbit 必须定义：7 个必选方法（`connect`/`disconnect`/`send`/`send_typing`/`send_image`/`get_chat_info`/
`check_<p>_requirements`）、5 个可选发送方法（document/voice/video/animation/image_file）、
5 个交互 UX 方法（`send_clarify`/`send_exec_approval`/`send_slash_confirm`/`send_model_picker`/
`send_choice_picker`，**且必须优雅降级为纯文本**）、**共享按钮回调 id 约定**
（`cl:<id>:<idx>` / `appr:<id>:<choice>` / `sc:<choice>:<id>`）、以及 5 个边缘 hook
（`env_enablement_fn` / `apply_yaml_config_fn` / `cron_deliver_env_var` / `standalone_sender_fn` /
`register_platform_handler`）。缺 `standalone_sender_fn` 会让 cron 投递静默失败
（`No live adapter for platform '<name>'`）——这是最难排查的坑。

### 4️⃣ Gateway 进程模型 + 四个状态文件
**为什么必须补**：多平台长期驻留必须有**单 dispatcher 互斥**与**可恢复状态**。
必须实现：①同 profile 单 dispatcher 强制（Hermes 用"无 `--force` 则拒绝启动"来防
"second dispatcher escapes the service and can corrupt shared gateway state"）；
②`gateway-starts.log`（启动戳序列 → 崩溃循环检测）；
③`processes.json`（后台进程登记簿：`(session_id, pid, host_start_time)` 三元组防 PID 复用 +
`watcher_*`/`watch_patterns` 输出守望 + 会话作用域）；
④`spawn-ledger.json`（机器级 spawn 账本：`(pid, create_time, purpose, spawner)` → 启动期回收孤儿）；
⑤`channel_directory.json`（`updated_at` + `platforms{}`，支持"主动枚举"与"会话反推"双数据源）。

### 5️⃣ 脚本化出站 + 跨机 + 事件入口三件套（`send` / `peer` / `webhook`）
**为什么必须补**：这是"agent 之外的系统"接入 Orbit 的全部通道，且都要求**不依赖 agent loop**。
- `send`：`platform[:chat_id[:thread_id]]` 与 `platform:#channel-name` 目标语法，**每平台一套原生 ID 正则**
  （§3.6 的 12 条正则），`MEDIA:<path>` 附件约定，退出码 `0/1/2` 契约，`--list` 目标枚举。
- `peer`：`<peer>[/<agent>]` 跨机 DM，同步 `dm` + 异步 `run`/`status`/`stop` 三件套，
  `--idempotency-key`，退出码 `0/1/2`。
- `webhook`：`/webhooks/<name>` 路由 + HMAC `--secret` + `{dot.notation}` 模板 +
  `--deliver-only`（**零 LLM 成本**）+ `--script` 过滤（stdin JSON，空输出/`[SILENT]`/非零退出 ⇒ 忽略）。

### 6️⃣ 插件安装安全闸 + Dashboard 插件契约
**为什么必须补**：插件是**同进程执行任意 Python**（`plugin_guard.py` 原文），没有沙箱兜底，
所以"安装期扫描"是唯一防线；同时 dashboard 插件是唯一有**跨前后端契约**的扩展点。
- 安全闸：`safe`/`caution`/`dangerous` 三级裁决，**`--force` 不得覆盖 `dangerous`**；
  代码文件豁免 15 个"读自己 key / 用 key 发 HTTP"模式，但**文档与配置文件跑全量模式集**；
  保留 critical 信号（外部凭证库**读取**、反弹 shell、持久化、混淆执行、外泄服务）；
  结构限额 400 文件 / 10 MB / 单文件 1 MB + symlink 逃逸检测；结果带 `scan_provenance` 可审计。
- Dashboard 契约：`manifest.json` 8 字段（`name`/`label`/`description`/`icon`/`version`/
  `tab{path,position}`/`entry`/`css`/`api`）+ `plugin_api.py` 必须暴露模块级 `router = APIRouter()`、
  挂载于 `/api/plugins/<name>/`、**必须能在无 dashboard 依赖下 import**（单测兜底）、
  **认证统一由 dashboard 中间件施加**（HTTP 用 session bearer token，WS 用 `?token=` / `?ticket=` / `?internal=` 三模式）。
- 另需：`allow_tool_override` 授权位 + profile 作用域覆盖层（`_scoped_tools`）+ 卸载时按身份回滚
  （`restore_registration` 的 `is not current` 检查）——否则插件覆盖会互相踩踏。
